Part 1: Docker Compose with TaskManager Pro

1.1 The Problem: Manual Container Management

Remember the pain of managing TaskManager Pro with three separate docker run commands? 

# The old way - complex and error-prone
docker network create taskmanager-network

docker run -d \
  --name taskmanager-mongodb \
  --network taskmanager-network \
  -v taskmanager-mongo-data:/database_data \
  -p 27017:27017 \
  taskmanager-mongodb

docker run -d \
  --name taskmanager-redis \
  --network taskmanager-network \
  -v taskmanager-redis-data:/data \
  -p 6379:6379 \
  taskmanager-redis

docker run -d \
  --name taskmanager-web \
  --network taskmanager-network \
  -v taskmanager-uploads:/var/www/html/uploads_local \
  -p 8080:8080 \
  -e MONGO_HOST=taskmanager-mongodb \
  -e REDIS_HOST=taskmanager-redis \
  taskmanager-web

Key Issues:

  • ❌ Order matters: Must start services in correct sequence
  • ❌ Manual network creation: Easy to forget or misconfigure
  • ❌ Error-prone: Long commands with many flags
  • ❌ No single source of truth: Configuration scattered across scripts

1.2 Docker Compose Solution

One YAML file to rule them all: 

# docker-compose.yml - simplified version
services:
  mongodb:
    build:
      context: ..
      dockerfile: docker/mongodb.Dockerfile
    image: taskmanager-mongodb
    volumes:
      - mongo-data:/database_data
  
  redis:
    build:
      context: ..
      dockerfile: docker/redis.Dockerfile
    image: taskmanager-redis
    volumes:
      - redis-data:/data
  
  web:
    build:
      context: ..
      dockerfile: docker/web.Dockerfile
    image: taskmanager-web
    environment:
      MONGO_HOST: mongodb
      REDIS_HOST: redis
    depends_on:
      - mongodb
      - redis
    ports:
      - "8080:8080"

volumes:
  mongo-data:
  redis-data:

networks:
  taskmanager-network:

Benefits:

  • ✅ Single command: docker compose up starts everything
  • ✅ Automatic networking: Services can reference each other by name
  • ✅ Service discovery: MongoDB available at hostname "mongodb"
  • ✅ Dependency management: Web waits for databases to start

Part 2: Docker Swarm with TaskManager Pro

2.1 Why Swarm for Production

Compose Limitations
  • ❌ No automatic recovery
  • ❌ No rolling updates
  • ❌ Manual scaling
  • ❌ Basic networking
Swarm Benefits
  • ✅ Self-healing services
  • ✅ Zero-downtime updates
  • ✅ Built-in load balancing
  • ✅ Production-grade orchestration

2.2 Converting to Swarm

Stop all running containers and remove all containers:

docker compose down

Initialize Swarm:

docker swarm init

Add Production Features:

# docker-compose.yml - complete production deployment
services:
  mongodb:
    image: taskmanager-mongodb
    volumes:
      - mongo-data:/database_data
    healthcheck:
      test: ["CMD", "mongosh", "--eval", "db.adminCommand('ping')"]
      interval: 10s
      timeout: 5s
      retries: 5
    deploy:
      replicas: 1
      restart_policy:
        condition: any
        delay: 5s
      resources:
        limits:
          memory: 1G
  
  redis:
    image: taskmanager-redis
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5
    deploy:
      replicas: 1
      restart_policy:
        condition: any
        delay: 5s
      resources:
        limits:
          memory: 512M
  
  web:
    image: taskmanager-web
    environment:
      MONGO_HOST: mongodb
      REDIS_HOST: redis
    ports:
      - "8080:8080"
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/api/tasks"]
      interval: 10s
      timeout: 5s
      retries: 3
    deploy:
      replicas: 3
      update_config:
        parallelism: 1
        delay: 10s
        order: start-first
        failure_action: rollback
      restart_policy:
        condition: any
        delay: 5s
      resources:
        limits:
          memory: 512M

volumes:
  mongo-data:
  redis-data:

New Swarm-Specific Settings Explained

These are the production features that Swarm adds beyond basic Compose:

deploy: Section
  • replicas: Number of container instances (3 for web, 1 for databases)
  • restart_policy: Automatic restart on failure with 5s delay
  • update_config: Rolling update strategy (web service only)
  • resources: Memory limits to prevent resource exhaustion
update_config: Details
  • parallelism: 1 - Update one container at a time
  • delay: 10s - Wait 10 seconds between updates
  • order: start-first - Start new before stopping old
  • failure_action: rollback - Auto-rollback on failure
Network Configuration

Default networking: Swarm automatically creates an overlay network for the stack. Services can communicate using their service names (mongodb, redis, web) without explicit network configuration.

Key Differences from Compose
  • No depends_on in Swarm: Swarm ignores depends_on; use health checks for startup ordering
  • Resource limits enforced: Swarm actually enforces memory limits (Compose doesn't)
  • Automatic load balancing: Multiple web replicas automatically load balanced
  • Self-healing: Failed containers automatically restarted on healthy nodes

Deploy and Monitor Commands:

# Monitor deployment progress

# Check service health and status
