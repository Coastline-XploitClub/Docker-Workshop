2. What is Kubernetes?

Kubernetes is a powerful container orchestration platform that automates the deployment, scaling, and management of containerized applications. Born from Google's experience running billions of containers in production, it has become the industry standard for managing complex containerized workloads at scale.

The Evolution to Kubernetes

2000s: Traditional Deployment Era

Applications ran directly on bare metal servers with monolithic architectures. Teams of sysadmins manually managed infrastructure, and scaling was labor-intensive and expensive.

2010s: Virtualization Era

Cloud computing and VMs revolutionized deployment. Tools like Puppet and Chef enabled infrastructure as code, but managing resources at scale remained challenging despite improved tooling.

2020s: Container Orchestration Era

Kubernetes enables treating clusters of machines as a single resource. It provides standard interfaces for scheduling, health checks, service discovery, and autoscaling—solving the complexity of container management at scale.

Why Kubernetes?

Kubernetes addresses the core challenges of running containers in production by providing:

  • Efficient Scheduling: Optimally distributes workloads across nodes
  • Service Discovery: Automatically locates services within the cluster
  • Health Monitoring: Continuously checks and maintains application health
  • Configuration Management: Standardizes application configuration
  • Autoscaling: Adjusts resources based on demand
  • Persistent Storage: Manages data beyond container lifecycles
  • Load Balancing: Distributes traffic across containers
  • Rolling Updates: Zero-downtime deployments and rollbacks

3. Kubernetes Architecture

Understanding Kubernetes architecture is essential for effectively deploying and managing containerized applications. Kubernetes follows a distributed system design with clear separation between control and data planes, ensuring high availability, scalability, and resilience.

Planes and Nodes

Kubernetes clusters are organized into two primary planes that work together to orchestrate containers:

Node

A physical or virtual machine that runs containerized workloads. Multiple nodes are joined together to form a cluster, providing the compute resources for your applications.

Control Plane

The cluster's brain—manages the overall state, makes scheduling decisions, and responds to cluster events. Runs on dedicated control plane nodes.

Data Plane

Where your applications run—consists of worker nodes that execute containerized workloads. Managed by the control plane components.

Kubernetes System Components

Each plane consists of specialized components that work together to provide Kubernetes' powerful orchestration capabilities:

Control Plane Components
  • etcd: Distributed key-value store serving as the cluster's source of truth for all configuration and state.
  • kube-apiserver: The frontend for the control plane, exposing the Kubernetes API for all communications.
  • kube-scheduler: Intelligently assigns pods to nodes based on resource requirements and constraints.
  • kube-controller-manager: Runs controllers that regulate cluster state and perform routine tasks.
  • cloud-controller-manager: Integrates with cloud providers to manage cloud-specific resources.
Data Plane Components
  • kubelet: Node agent that ensures containers are running in pods and manages their lifecycle.
  • kube-proxy: Network proxy maintaining network rules for pod communication across the cluster.
Key Takeaway

The separation between control and data planes ensures that even if worker nodes fail, the control plane can reschedule workloads to healthy nodes. This architecture provides the resilience and scalability needed for production containerized applications.

4. Kubernetes in Docker (KinD)

KinD (Kubernetes in Docker) is a tool that allows you to run Kubernetes clusters using Docker containers as nodes. It's designed for local development, CI/CD, and testing scenarios where you need a lightweight, fast-starting Kubernetes environment without the overhead of virtual machines.

Why Use KinD for CCDC Training?

  • Rapid Deployment: Cluster creation in under 2 minutes
  • Resource Efficient: Minimal CPU and memory overhead
  • Reproducible: Consistent environments across team members
  • Full Kubernetes: Real K8s API, not a simulation
  • Easy Cleanup: Complete removal with one command
  • Local Storage: Persistent volumes using host directories

Setting Up KinD

Step 1: Create Cluster Configuration

First, change into the Deploy-Kubernetes/ directory and create a KinD configuration file that defines a 3-node cluster (1 control-plane + 2 workers) with persistent volume mount points for: 

# Change into the Deploy-Kubernetes directory
cd Deploy-Kubernetes

# Create the configuration file
cat > kind-config.yaml << EOF
# three node (two workers) cluster config
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
    extraMounts:
      - hostPath: /tmp/kind-mount-1
        containerPath: /some/path/in/container
  - role: worker
    extraMounts:
      - hostPath: /tmp/kind-mount-2
        containerPath: /some/path/in/container
EOF
Configuration Breakdown
  • Control-plane node: Runs Kubernetes API server and control components
  • Worker nodes: Run your application pods and workloads
  • extraMounts: Enable persistent volume storage using host directories
Step 2: Create the Kubernetes Cluster

Create your local Kubernetes cluster using the generated configuration: 

kind create cluster --config kind-config.yaml
Expected Output

You should see output similar to:
Creating cluster "kind" ...
✓ Ensuring node image (kindest/node:v1.30.0) 🖼
✓ Preparing nodes 📦
✓ Writing configuration 📜
✓ Starting control-plane 🕹️
✓ Installing CNI 🔌
✓ Installing StorageClass 💾
Set kubectl context to "kind-kind"

Step 3: Verify Cluster Status

Confirm your cluster is running and accessible:

# Check cluster info
kubectl cluster-info

# View nodes
kubectl get nodes

# Check system pods
kubectl get pods -n kube-system

# Check all pods
kubectl get pods -A
Step 4: Cleanup (When Finished)

When you're done with your cluster, remove it completely:

kind delete cluster
Ready for Kubernetes!

Your local Kubernetes cluster is now ready for deployment exercises. You can proceed to deploy applications, create services, and explore Kubernetes resource types in a safe, local environment that mirrors production Kubernetes behavior.

5. Kubernetes Resource Types

Kubernetes resource types are the building blocks of your Kubernetes cluster. They are used to create, manage, and delete Kubernetes objects.

5.1. Namespace

Namespaces provide a mechanism for isolating groups of resources within a single cluster. They're a way to divide cluster resources between multiple users, teams, or projects—like virtual clusters within your physical cluster.

Why Use Namespaces?
  • Resource Isolation: Separate development, staging, and production environments
  • Team Organization: Different teams can work independently in their own namespaces
  • Access Control: Apply RBAC policies at the namespace level
  • Resource Quotas: Limit CPU, memory, and object counts per namespace
  • Name Scoping: Resource names only need to be unique within a namespace
Hands-On: Creating Namespaces

Let's practice creating namespaces using both imperative and declarative approaches:

Exercise 1: Create a Namespace Using CLI

Use the kubectl command to create a namespace directly:

# Create a namespace called 'namespace-cli' using kubectl
kubectl create namespace namespace-cli

# Verify the namespace was created
kubectl get namespaces | grep namespace-cli
Exercise 2: Create a Namespace Using YAML

First, navigate to the Namespace directory and examine the provided YAML file: 

# Navigate to the Namespace directory
cd ~/Docker-Workshop/assets/lecture/Kubernetes-Resource-Types/Namespace/

# View the Namespace.yaml file
cat Namespace.yaml

The file contains:

apiVersion: v1
kind: Namespace
metadata:
  name: production

Now apply this configuration to create the namespace:

# Apply the namespace configuration
kubectl apply -f Namespace.yaml

# Verify both namespaces were created
kubectl get namespaces | grep -E 'namespace-cli|production'
Understanding the YAML Structure
  • apiVersion: v1 - The Kubernetes API version for namespaces
  • kind: Namespace - Specifies this resource is a Namespace
  • metadata.name - The name of the namespace to create
Exercise 3: Clean Up Namespaces

Delete both namespaces to keep your cluster clean:

# Delete the namespace created via CLI
kubectl delete namespace namespace-cli

# Delete the namespace created via YAML file
kubectl delete -f Namespace.yaml

# Verify the namespaces have been deleted
kubectl get namespaces

# You should no longer see 'namespace-cli' or 'production' in the list
Important Notes
  • Deleting a namespace will delete ALL resources within it
  • The deletion may take a few seconds to complete
  • Always verify your namespaces are deleted to avoid resource leaks
Important Cleanup Note

Always clean up test resources! Deleting a namespace will delete ALL resources within it, including pods, services, deployments, and any other objects. The --ignore-not-found=true flag prevents errors if resources don't exist, making cleanup commands idempotent and safe to run multiple times.

5.2. Pod

A Pod is the smallest deployable unit in Kubernetes, representing a single instance of a running process in your cluster. Pods contain one or more containers that share storage, network, and a specification for how to run them.

Understanding Pods
  • Atomic Unit: Pods are the basic execution unit - containers in a Pod are always co-located and co-scheduled
  • Shared Resources: Containers in a Pod share the same network namespace (IP and ports) and storage volumes
  • Ephemeral Nature: Pods are designed to be disposable - use higher-level objects like Deployments for persistent workloads
  • Best Practice: Usually one container per Pod unless containers are tightly coupled
Hands-On: Working with Pods

Let's explore Pods by creating increasingly sophisticated configurations, starting with a minimal example and progressing to a production-ready Pod specification.

Exercise 1: Create the Namespace

First, create a dedicated namespace for our Pod examples:

# Navigate to the Pod directory
cd ~/Docker-Workshop/assets/lecture/Kubernetes-Resource-Types/Pod/

# Create the namespace using the provided YAML
kubectl apply -f Namespace.yaml

# Set it as the current namespace context
kubectl config set-context --current --namespace=04--pod
Exercise 2: The Wrong Way (Imperative)

First, let's see what NOT to do. Creating Pods imperatively is discouraged in production: 

# ⚠️ DO NOT DO THIS IN PRODUCTION ⚠️
# This creates a pod imperatively - difficult to track and reproduce
kubectl run --image=nginx:1.26.0 -n 04--pod created-the-wrong-way

# Check the pod was created
kubectl get pods -n 04--pod

# Clean it up
kubectl delete pod created-the-wrong-way -n 04--pod
Why Avoid Imperative Commands?
  • No version control or audit trail
  • Difficult to reproduce in other environments
  • Can't review changes before applying
  • Doesn't support GitOps workflows
Exercise 3: Minimal Pod Configuration

Now let's create a Pod using a minimal declarative YAML configuration: 

# View the minimal Pod configuration
cat Pod.nginx-minimal.yaml

# Apply the minimal configuration
kubectl apply -n 04--pod -f Pod.nginx-minimal.yaml

# Check the pod status
kubectl get pods -n 04--pod
kubectl describe pod nginx-minimal -n 04--pod

Test the minimal Pod with port forwarding:

# Forward local port 8080 to the Pod's port 80
kubectl port-forward -n 04--pod nginx-minimal 8080:80

# In another terminal, test the connection
curl http://localhost:8080

# Press Ctrl+C to stop port forwarding
Exercise 4: Production-Ready Pod Configuration

Now let's deploy a better, production-ready Pod with security hardening, resource limits, and health checks: 

# View the improved Pod configuration
cat Pod.nginx-better.yaml

# Apply the better configuration
kubectl apply -n 04--pod -f Pod.nginx-better.yaml

# Check both pods
kubectl get pods -n 04--pod -o wide

# Compare the configurations
kubectl get pod nginx-minimal -n 04--pod -o yaml
kubectl get pod nginx-better -n 04--pod -o yaml
Production Pod Best Practices

The nginx-better Pod demonstrates several important practices:

  • Security-hardened image: Uses Chainguard's distroless nginx image for minimal attack surface
  • Non-root user: Runs as user 1001 instead of root (UID 0)
  • Resource limits: Sets memory and CPU constraints to prevent resource exhaustion
  • Health checks: Readiness probe ensures the container is ready to serve traffic
  • Security context: Disables privilege escalation and enforces seccomp profile
  • Explicit port declaration: Documents which ports the container exposes

Test the production-ready Pod:

# Port forward to the better pod (note: uses port 8080 internally)
kubectl port-forward -n 04--pod nginx-better 8080:8080

# Test the connection
curl http://localhost:8080

# Check resource usage
kubectl top pod -n 04--pod

# View security context
kubectl get pod nginx-better -n 04--pod -o jsonpath='{.spec.securityContext}' | jq .
Exercise 5: Examining Pod Details

Learn to inspect and troubleshoot Pods:

# View pod logs
kubectl logs nginx-minimal -n 04--pod
kubectl logs nginx-better -n 04--pod

# Execute commands inside a pod
kubectl exec -it nginx-minimal -n 04--pod -- /bin/bash
# Try: ls -la, ps aux, whoami, then exit

# Note: The better pod might not have bash due to distroless image
kubectl exec nginx-better -n 04--pod -- whoami

# View pod events
kubectl get events -n 04--pod --sort-by='.lastTimestamp'
Exercise 6: Clean Up

Remove all Pod resources by deleting the namespace:

# Delete the namespace (this removes all resources within it)
kubectl delete -f Namespace.yaml

# Verify cleanup
kubectl get namespaces | grep 04--pod
# Should return no results
Important Pod Considerations
  • Pods are ephemeral: Don't use naked Pods for production workloads - use Deployments or StatefulSets
  • Pod IPs change: When a Pod is recreated, it gets a new IP - use Services for stable networking
  • Resource limits matter: Always set resource requests and limits to ensure cluster stability
  • Security by default: Always configure security contexts and use minimal, hardened container images
