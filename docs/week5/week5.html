Common Docker Security Misconfigurations

1. The Root User Problem

The most prevalent Docker security issue remains containers running as root user. When attackers compromise a root container, they gain administrative privileges that can lead to host system compromise.

Vulnerable Configuration 
# Dockerfile with root user vulnerability
FROM ubuntu:20.04

RUN apt-get update && apt-get install -y nginx python3

WORKDIR /app

COPY app.py .

RUN python3 app.py

RUN sed -i 's/listen 80 default_server;/listen 8080 default_server;/' /etc/nginx/sites-available/default && \
    sed -i 's/listen \[::\]:80 default_server;/listen [::]:8080 default_server;/' /etc/nginx/sites-available/default && \
    sed -i 's|root /var/www/html;|root /usr/share/nginx/html;|' /etc/nginx/sites-available/default

EXPOSE 8080

CMD ["nginx", "-g", "daemon off;"]

# No USER directive - runs as root by default! 😱
Critical Risk
Secure Alternative 
# Dockerfile with proper user isolation
FROM ubuntu:20.04

RUN apt-get update && apt-get install -y nginx python3

RUN groupadd -g 1001 appgroup && \
    useradd -u 1001 -g appgroup -m -s /bin/bash appuser

RUN mkdir -p /app /usr/share/nginx/html /var/log/nginx /var/cache/nginx /var/lib/nginx /run/nginx && \
    chown -R appuser:appgroup /app /usr/share/nginx/html /var/log/nginx /var/cache/nginx /var/lib/nginx /run/nginx

RUN sed -i 's/listen 80 default_server;/listen 8080 default_server;/' /etc/nginx/sites-available/default && \
    sed -i 's/listen \[::\]:80 default_server;/listen [::]:8080 default_server;/' /etc/nginx/sites-available/default && \
    sed -i 's|root /var/www/html;|root /usr/share/nginx/html;|' /etc/nginx/sites-available/default

RUN sed -i 's|user www-data;|user appuser appgroup;|' /etc/nginx/nginx.conf && \
    sed -i 's|pid /run/nginx.pid;|pid /run/nginx/nginx.pid;|' /etc/nginx/nginx.conf

WORKDIR /app

COPY --chown=appuser:appgroup app.py .

USER appuser

RUN python3 app.py

EXPOSE 8080

CMD ["nginx", "-g", "daemon off;"]
Secure

2. Secrets Embedded in Image Layers

Hardcoded secrets represent another critical vulnerability pattern. Even when developers attempt to remove secrets in subsequent layers, they remain accessible in the image history. Our demonstration shows how BuildKit secrets and multi-stage builds provide secure alternatives.

Vulnerable Configuration 
# VULNERABLE: Demonstrates how secrets remain in image layers!
FROM python:3.9-slim

RUN groupadd -g 1001 appgroup && \
    useradd -u 1001 -g appgroup -m -s /bin/bash appuser

WORKDIR /app

RUN chown -R appuser:appgroup /app

COPY --chown=appuser:appgroup app.py ./

RUN echo "API_KEY=sk-1234567890abcdef-SUPER-SECRET-KEY-DO-NOT-EXPOSE" > /app/.env && \
    echo "DATABASE_PASSWORD=admin123!VerySecretPassword" >> /app/.env && \
    echo "AWS_SECRET_ACCESS_KEY=AKIAIOSFODNN7EXAMPLE12345" >> /app/.env && \
    echo "JWT_SECRET=my-super-secret-jwt-signing-key-2024" >> /app/.env

RUN rm -f /app/.env

ENV ANOTHER_SECRET="hardcoded-secret-in-dockerfile-2024"

ENV DB_CONNECTION_STRING="postgresql://admin:secret123@db:5432/myapp"

ARG BUILD_SECRET="build-time-secret-becomes-visible"

ENV BUILD_SECRET_EXPOSED=$BUILD_SECRET

USER appuser

EXPOSE 8000

CMD ["sh", "-c", "python app.py && python -m http.server 8000"]
Critical Risk
Secure BuildKit + Multi-stage 
# SECURE: Multi-stage build with BuildKit secrets that don't persist in layers

FROM python:3.9-slim AS builder
WORKDIR /build

RUN --mount=type=secret,id=api_key \
    --mount=type=secret,id=db_password \
    --mount=type=secret,id=aws_secret \
    --mount=type=secret,id=jwt_secret \
    echo "Build completed with mounted secrets (not embedded in layers)"

FROM python:3.9-slim AS runtime

RUN groupadd -g 1001 appgroup && \
    useradd -u 1001 -g appgroup -m -s /bin/bash appuser

WORKDIR /app
RUN chown -R appuser:appgroup /app

COPY --chown=appuser:appgroup app.py ./

ARG BUILD_ENV=production
ENV BUILD_ENV=$BUILD_ENV

USER appuser
EXPOSE 8000

CMD ["sh", "-c", "python app.py && python -m http.server 8000"]
Secure
Key Differences
  • BuildKit Secrets: Available during build but not embedded in layers
  • Multi-stage Build: Separates build operations from runtime image
  • Runtime Injection: Secrets provided via -e flags at container startup
  • Verification: Use docker history --no-trunc to detect embedded secrets

3. Exposed Docker Socket

Mounting the Docker socket into containers represents one of the most dangerous misconfigurations. This practice grants containers the ability to control the Docker daemon, effectively providing root access to the host system.

Dangerous Socket Exposure 
# EXTREMELY DANGEROUS docker-compose.yml
services:
  app:
    image: myapp
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock  # DANGEROUS
      - /:/host  # Full host filesystem access
    privileged: true  # All kernel capabilities
Critical Risk
Secure Configuration 
# Secure docker-compose.yml
services:
  app:
    image: myapp:1.2.3
    read_only: true
    user: "1000:1000"
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE
    security_opt:
      - no-new-privileges:true
      - apparmor:docker-default
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: '0.5'
Secure

Docker Scout Implementation

Docker Scout has evolved from a simple vulnerability scanner into a comprehensive supply chain security platform, making it an ideal tool for container security analysis.

Installation and Basic Scanning

# Docker Scout comes with Docker Desktop 4.17.0+
# For manual installation:
curl -fsSL https://raw.githubusercontent.com/docker/scout-cli/main/install.sh -o install-scout.sh
sh install-scout.sh

# Basic vulnerability scan
docker scout quickview nginx:latest

# Detailed CVE analysis with EPSS scores
docker scout cves --epss --only-severity critical,high nginx:alpine

# Generate comprehensive report
docker scout cves --format json --output report.json nginx:latest

Trivy Scanner

Trivy is the industry standard for comprehensive container security scanning, with 27,000+ GitHub stars and adoption by major platforms like GitLab and Harbor.

Installation and Configuration

# Binary installation (recommended for labs)
curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sudo sh -s -- -b /usr/local/bin

Multi-layer Security Analysis

# Scan Dockerfile for misconfigurations
trivy config Dockerfile

# Detect embedded secrets
trivy fs --scanners secret /path/to/repo

# Comprehensive image scan
trivy image --config trivy.yaml nginx:latest

# Generate SBOM for supply chain analysis
trivy image --format cyclonedx --output sbom.json nginx:latest

# CI/CD integration with exit codes
trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:latest

Security Best Practices Checklist

Image Security

  • ✓ Use specific version tags, never latest
  • ✓ Implement multi-stage builds
  • ✓ Scan images before deployment
  • ✓ Sign images with Docker Content Trust
  • ✓ Use distroless or minimal base images
  • ✓ Regular automated rebuilds for patches

Runtime Security

  • ✓ Drop all capabilities, add only required ones
  • ✓ Run containers as non-root users
  • ✓ Implement read-only root filesystems
  • ✓ Set resource limits (memory, CPU, file descriptors)
  • ✓ Enable AppArmor/SELinux profiles
  • ✓ Implement network segmentation
