Container adoption has exploded, but with it comes complex security challenges. This week focuses on identifying, understanding, and remediating the most common Docker security misconfigurations that attackers exploit in real-world scenarios.

Common Docker Security Misconfigurations

1. The Root User Problem

The most prevalent Docker security issue remains containers running as root user. When attackers compromise a root container, they gain administrative privileges that can lead to host system compromise.

Vulnerable Configuration 
# Dockerfile with root user vulnerability
FROM ubuntu:20.04
RUN apt-get update && apt-get install -y nginx
COPY app.py /app/
EXPOSE 80
CMD ["python", "/app/app.py"]
# No USER directive - runs as root by default!
Critical Risk
Secure Alternative 
# Dockerfile with proper user isolation
FROM ubuntu:20.04
RUN apt-get update && apt-get install -y nginx
RUN groupadd -r appuser && useradd -r -g appuser appuser
COPY app.py /app/
RUN chown -R appuser:appuser /app
USER appuser
EXPOSE 80
CMD ["python", "/app/app.py"]
Secure

2. Secrets Embedded in Image Layers

Hardcoded secrets represent another critical vulnerability pattern. Even when developers attempt to remove secrets in subsequent layers, they remain accessible in the image history.

Vulnerable Configuration 
# Secrets remain in image layers!
FROM python:3.9
COPY . /app
RUN echo "API_KEY=sk-abc123..." > /app/.env
RUN pip install -r requirements.txt
RUN rm /app/.env  # Secret still in layer!
Critical Risk
Secure Multi-stage Build 
# Secure multi-stage build
FROM python:3.9 as builder
ARG API_KEY
RUN --mount=type=secret,id=apikey \
    API_KEY=$(cat /run/secrets/apikey) && \
    pip install --user -r requirements.txt

FROM python:3.9-slim
COPY --from=builder /root/.local /root/.local
# Secrets never reach final image
Secure

3. Exposed Docker Socket

Mounting the Docker socket into containers represents one of the most dangerous misconfigurations. This practice grants containers the ability to control the Docker daemon, effectively providing root access to the host system.

Dangerous Socket Exposure 
# EXTREMELY DANGEROUS docker-compose.yml
version: '3.8'
services:
  app:
    image: myapp
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock  # DANGEROUS
      - /:/host  # Full host filesystem access
    privileged: true  # All kernel capabilities
Critical Risk
Secure Configuration 
# Secure docker-compose.yml
version: '3.8'
services:
  app:
    image: myapp:1.2.3
    read_only: true
    user: "1000:1000"
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE
    security_opt:
      - no-new-privileges:true
      - apparmor:docker-default
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: '0.5'
Secure

Docker Scout Implementation

Docker Scout has evolved from a simple vulnerability scanner into a comprehensive supply chain security platform, making it an ideal tool for container security analysis.

Installation and Basic Scanning

# Docker Scout comes with Docker Desktop 4.17.0+
# For manual installation:
curl -fsSL https://raw.githubusercontent.com/docker/scout-cli/main/install.sh -o install-scout.sh
sh install-scout.sh

# Basic vulnerability scan
docker scout quickview nginx:latest

# Detailed CVE analysis with EPSS scores
docker scout cves --epss --only-severity critical,high nginx:alpine

# Generate comprehensive report
docker scout cves --format json --output report.json nginx:latest

Policy Evaluation and Supply Chain Security

# Enable supply chain attestations
docker build --provenance=true --sbom=true --push -t myapp:v1 .

# Evaluate against security policies
docker scout policy --org myorg myapp:v1

# View policy violations
docker scout policy --org myorg --details myapp:v1
Understanding EPSS Scores

EPSS (Exploit Prediction Scoring System) scores indicate the probability that a CVE will be exploited. A score of 0.95 means 95% probability of exploitation, helping prioritize remediation efforts.

Trivy Scanner

Trivy is the industry standard for comprehensive container security scanning, with 27,000+ GitHub stars and adoption by major platforms like GitLab and Harbor.

Installation and Configuration

# Binary installation (recommended for labs)
curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sudo sh -s -- -b /usr/local/bin

# Create comprehensive scanning configuration
cat > trivy.yaml << EOF
scan:
  scanners: ["vuln", "secret", "misconfig"]
  severity: ["MEDIUM", "HIGH", "CRITICAL"]
vulnerability:
  ignore-unfixed: true
license:
  forbidden: ["GPL-3.0", "AGPL-3.0"]
EOF

Multi-layer Security Analysis

# Scan Dockerfile for misconfigurations
trivy config Dockerfile

# Detect embedded secrets
trivy fs --scanners secret /path/to/repo

# Comprehensive image scan
trivy image --config trivy.yaml nginx:latest

# Generate SBOM for supply chain analysis
trivy image --format cyclonedx --output sbom.json nginx:latest

# CI/CD integration with exit codes
trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:latest

Sample Misconfiguration Detection

Trivy Dockerfile Scan Results
Dockerfile (dockerfile)
=======================
MEDIUM: Specify a tag in the 'FROM' statement
LOW: Add HEALTHCHECK instruction  
HIGH: User should be specified
CRITICAL: Do not use 'latest' tag for base images

Security Best Practices Checklist

Image Security

  • ✓ Use specific version tags, never latest
  • ✓ Implement multi-stage builds
  • ✓ Scan images before deployment
  • ✓ Sign images with Docker Content Trust
  • ✓ Use distroless or minimal base images
  • ✓ Regular automated rebuilds for patches

Runtime Security

  • ✓ Drop all capabilities, add only required ones
  • ✓ Run containers as non-root users
  • ✓ Implement read-only root filesystems
  • ✓ Set resource limits (memory, CPU, file descriptors)
  • ✓ Enable AppArmor/SELinux profiles
  • ✓ Implement network segmentation

CI/CD Security Pipeline

Integrate security scanning into your development workflow:

# GitHub Actions security workflow
name: Security Scan
on: [push, pull_request]
jobs:
  security-scan:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        scanner: [trivy, scout]
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        run: docker build -t myapp:${{ github.sha }} .
      
      - name: Run Trivy scan
        if: matrix.scanner == 'trivy'
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: myapp:${{ github.sha }}
          format: 'sarif'
          output: 'trivy-results.sarif'
          severity: 'CRITICAL,HIGH'
          exit-code: 1
      
      - name: Run Docker Scout
        if: matrix.scanner == 'scout'
        run: |
          docker scout cves --only-severity critical,high \
            --exit-code myapp:${{ github.sha }}

const express = require('express');
const morgan = require('morgan');
const app = express();

app.use(morgan('combined'));
app.get('/', (req, res) => {
  res.json({ 
    message: 'Vulnerable Docker App',

    env: process.env 
  });
});

  console.log('Server running on port 3000');

Step 5: Exploit the Vulnerabilities

# Run the vulnerable container
docker run -d --name vulnerable-container vulnerable-app:latest

# Verify it's running as root
docker exec vulnerable-container whoami
docker exec vulnerable-container id

# Check environment variables for secrets
docker exec vulnerable-container env | grep -E "(API_KEY|PASSWORD)"

Step 6: Create Secure Version

# Create secure Dockerfile
cat > Dockerfile.secure << 'EOF'
# Multi-stage build for security
FROM node:18-alpine as builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production && npm cache clean --force

FROM node:18-alpine
RUN addgroup -g 1001 -S nodejs && \
    adduser -S nodejs -u 1001
COPY --from=builder /app/node_modules ./node_modules
COPY --chown=nodejs:nodejs . .
USER nodejs
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD node healthcheck.js
CMD ["node", "app.js"]
EOF

# Create healthcheck script
cat > healthcheck.js << 'EOF'
const http = require('http');
const options = {
  host: 'localhost',
  port: 3000,
  timeout: 2000,
  path: '/'
};

const request = http.request(options, (res) => {
  process.exit(res.statusCode === 200 ? 0 : 1);
});

request.on('error', () => process.exit(1));
request.end();
EOF

Step 7: Compare Security Postures

# Build secure version

# Compare vulnerability counts

docker exec secure-container id

# Clean up

docker rm vulnerable-container secure-container

# Create secure container configuration
cat > docker-compose.secure.yml << 'EOF'
version: '3.8'
services:
  webapp:
    image: nginx:alpine
    read_only: true
    user: "101:101"  # nginx user
    cap_drop:
      - ALL
    cap_add:
      - CHOWN
      - SETGID
      - SETUID
      - NET_BIND_SERVICE
    security_opt:
      - no-new-privileges:true
      - apparmor:docker-default
    tmpfs:
      - /var/cache/nginx:size=100M
      - /var/run:size=100M
    deploy:
      resources:
        limits:
          memory: 256M
          cpus: '0.5'
    healthcheck:
      test: ["CMD", "wget", "--quiet", "--tries=1", "--spider", "http://localhost/"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 30s
EOF

# Deploy secure configuration
docker-compose -f docker-compose.secure.yml up -d

# Verify security constraints
docker-compose -f docker-compose.secure.yml exec webapp whoami
docker-compose -f docker-compose.secure.yml exec webapp id

# Clean up
docker-compose -f docker-compose.secure.yml down

Exercise 3: Runtime Security Monitoring

Step 1: Deploy Falco for Runtime Protection

# Install Falco (if not already installed)
curl -s https://falco.org/repo/falcosecurity-packages.asc | apt-key add -
echo "deb https://download.falco.org/packages/deb stable main" | tee -a /etc/apt/sources.list.d/falcosecurity.list
apt-get update -qq
apt-get install -y falco

# Create custom Falco rule for container security
cat > /etc/falco/local_rules.yaml << 'EOF'
- rule: Container Privilege Escalation
  desc: Detect privilege escalation in containers
  condition: >
    spawned_process and container and
    (proc.name in (sudo, su) or proc.args contains setuid)
  output: >
    Privilege escalation detected in container
    (command=%proc.cmdline container=%container.name user=%user.name)
  priority: WARNING

- rule: Sensitive File Access in Container
  desc: Detect access to sensitive files from container
  condition: >
    open_read and container and
    (fd.name in (/etc/shadow, /etc/passwd, /etc/sudoers) or
     fd.name startswith /proc/)
  output: >
    Sensitive file access from container
    (file=%fd.name container=%container.name command=%proc.cmdline)
  priority: ERROR
EOF

# Start Falco
systemctl start falco
systemctl enable falco

Step 2: Trigger Security Events

# Start a container and trigger suspicious activities
docker run -it --rm --name test-container ubuntu:20.04 bash

# Inside container, trigger Falco alerts:
# Try to read sensitive files
cat /etc/shadow 2>/dev/null || echo "Access denied"
cat /proc/version

# Try privilege escalation
su root 2>/dev/null || echo "su failed"

# Exit container
exit

# Check Falco logs for alerts
journalctl -u falco -f

Step 1: Enable Content Trust

# Enable Docker Content Trust
export DOCKER_CONTENT_TRUST=1

# Try to pull unsigned image (should fail)
docker pull hello-world:latest || echo "Unsigned image blocked!"

# Disable content trust for this exercise

# Analyze SBOM

Step 2: Security Policy as Code

# Create OPA policy for container security
mkdir -p opa-policies

cat > opa-policies/security.rego << 'EOF'
package docker.security

# Deny containers running as root
deny[msg] {
    input.User == "root"
    msg := "Container must not run as root user"
}

# Deny privileged containers
deny[msg] {
    input.HostConfig.Privileged == true
    msg := "Privileged containers are not allowed"
}

# Deny containers with ALL capabilities
deny[msg] {
    input.HostConfig.CapAdd[_] == "ALL"
    msg := "Containers must not have ALL capabilities"
}

# Require specific tags (no latest)
deny[msg] {
    endswith(input.Config.Image, ":latest")
    msg := "Images must use specific version tags, not 'latest'"
}
EOF
